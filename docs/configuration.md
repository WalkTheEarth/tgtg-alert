# Configuration

Everything is set through environment variables, read at startup from `.env` in
the working directory (or `--env-file`), then from the real environment.

```bash
# .env
TGTG_POLL_INTERVAL=900
TGTG_WEBHOOK_URL=https://ntfy.sh/my-topic
```

Real environment variables **override** the file, so a one-off change needs no
editing:

```bash
TGTG_LOG_LEVEL=DEBUG tgtg-alert poll --dry-run
```

### `TGTG_DATA_DIR`

Where the SQLite database, and therefore your session, lives.

```bash
TGTG_DATA_DIR=/var/lib/tgtg-alert
```

Default `./data`, resolved relative to the working directory. **Set it
explicitly when running as a service** — a relative path depends on where the
process starts, and a service that starts elsewhere finds an empty database and
reports that you are logged out.

The directory is created if missing. It must be writable by whatever user runs
the process.

> This directory contains a live Too Good To Go session. Back it up somewhere
> private; never commit it. See [Security](security.md).

---

### `TGTG_POLL_INTERVAL`

Seconds between poll passes. Default `600` (ten minutes). **Floor of `300`** —
values below that are raised silently, because polling faster is both useless
(TGTG stock does not churn that fast) and the quickest route to being blocked.

```bash
TGTG_POLL_INTERVAL=1200    # 20 minutes — cautious
TGTG_POLL_INTERVAL=300     # 5 minutes — the aggressive floor
```

**This is the setting that most affects whether you get blocked.** Too Good To
Go's anti-abuse measures respond to frequency and consistency rather than a
documented quota — there is no request budget you can spend down. Observed
guidance from the wider ecosystem runs from "once a minute often results in an IP
ban" up to the Home Assistant integration's conservative 60-minute baseline with
short bursts inside known sales windows.

The default of ten minutes sits between those: fast enough to catch most drops,
well clear of the range reported to get IPs banned.

**If you are being blocked, raise this before changing anything else.** Going
from 600 to 1200 costs you little and materially reduces your footprint. If you
only want alerts during, say, weekday lunchtimes, note that this tool polls
around the clock — a lower-frequency setting is the honest mitigation.

### `TGTG_API_TOKEN`

The bearer token the phone uses to talk to your server. Generated by
`tgtg-alert init` with `secrets.token_urlsafe(32)`.

```bash
TGTG_API_TOKEN=some-long-random-string
```

**Changing it unpairs every phone** — they hold the old value and will start
getting `401`s until re-paired. To rotate deliberately:

```bash
# 1. Edit TGTG_API_TOKEN in .env
# 2. Restart
# 3. Re-pair each phone
tgtg-alert pair
```

If it is unset at startup, a random one is generated **for that process only**.
That works, but every restart invalidates paired phones, so it is only sensible
for a throwaway test.

This token is unrelated to your Too Good To Go account. It grants access to your
*watches*, not to TGTG.

---

### `TGTG_HOST`

Interface the HTTP API binds to. Default `0.0.0.0` (all interfaces).

```bash
TGTG_HOST=127.0.0.1    # only reachable from this machine
```

Set it to `127.0.0.1` when the API sits behind a reverse proxy on the same host.
That is strictly better than binding publicly and relying on the token: a
loopback-only service cannot be reached by anything that has not already got
code execution on the box.

---

### `TGTG_PORT`

API port. Default `8787`.

```bash
TGTG_PORT=9000
```

Must match the URL you pair the phone with. If you change it, re-run
`tgtg-alert pair`.

### `TGTG_USER_AGENT`

The client fingerprint sent to Too Good To Go.

```bash
TGTG_USER_AGENT='TGTG/26.10.0 Dalvik/2.1.0 (Linux; U; Android 14; Pixel 8 Pro Build/AP2A.240905.003)'
```

**Leave this unset unless you have a reason.** Login resolves the current TGTG
Android version from the Play Store and stores it; the poller then reuses that
exact string. Setting this variable overrides both.

The reason the match matters: DataDome binds its session cookie to the
User-Agent *and IP* that solved its challenge. Log in under one string, poll
under another, and it reads as a stolen cookie — `403`.

Set it when:

- `login` reported `fallback (could not reach Play Store)`, meaning it guessed.
- Alerts stopped with 403s and the version has moved on. Check the Play Store
  listing for the current version and paste it into the template above.

Getting the format wrong is worse than leaving it unset — the string must match
the pattern TGTG's app sends.

### `TGTG_LANGUAGE`

The `accept-language` header. Default `en-GB`.

```bash
TGTG_LANGUAGE=en-US
TGTG_LANGUAGE=de-DE
```

Affects pickup-window and price formatting, and the language TGTG describes
items in. There are reports of persistent 403s that cleared when the locale
changed, so it is worth trying if you are blocked — but that is a workaround
rather than an explanation, and the effect is not well understood.

---

### `TGTG_HTTP_TIMEOUT`

Seconds before an outbound request to Too Good To Go is abandoned. Default `20`.

```bash
TGTG_HTTP_TIMEOUT=45    # slow or unreliable connection
```

Raise it on a flaky connection. Lowering it is rarely useful — a timeout is
treated as a bucket failure and retried next pass, so an over-eager timeout just
converts slow responses into missing data.

---

### `TGTG_LOG_LEVEL`

`DEBUG`, `INFO` (default), `WARNING`, or `ERROR`.

```bash
TGTG_LOG_LEVEL=DEBUG
```

`DEBUG` adds per-item matching detail and the reasons for quiet decisions —
useful when a watch matches nothing and you want to know why. It is verbose: one
line per candidate item per watch.

Worth knowing for production:

```bash
TGTG_LOG_LEVEL=WARNING
```

Silences the per-pass summary, leaving only problems. **If you do this, watch
the app's status screen instead** — a blocked tracker is otherwise completely
silent, which is the failure mode this project works hardest to avoid.

### `TGTG_WEBHOOK_URL`

POST every alert here as well as pushing to phones.

```bash
TGTG_WEBHOOK_URL=https://ntfy.sh/my-tgtg-topic
```

The body is small and stable:

```json
{
  "title": "Magic Bag is back at Blank Street",
  "body": "3 left · 3.99 · collect by 19:00",
  "data": {"watchId": 1, "itemId": "123456"}
}
```

Worth setting even if you use the app, because it:

- lets you get alerts **with no phone app at all**,
- is the easiest way to verify the pipeline end to end, and
- gives you a fallback if push delivery is unreliable.

Recipes:

```bash
# ntfy — push to a phone or desktop, no account needed
TGTG_WEBHOOK_URL=https://ntfy.sh/your-secret-topic

# Discord
TGTG_WEBHOOK_URL=https://discord.com/api/webhooks/...

# Home Assistant
TGTG_WEBHOOK_URL=http://homeassistant.local:8123/api/webhook/...
```

A webhook failure is logged and counted, and does **not** stop phone delivery.
Both channels are attempted independently.

> Discord and Slack expect their own payload shape and will reject this generic
> one. Use a relay (an ntfy topic, a small script, or Home Assistant) when
> posting to those.

### `EXPO_ACCESS_TOKEN`

Optional. Locks your Expo push project so only you can send to your devices.

```bash
EXPO_ACCESS_TOKEN=your-expo-access-token
```

Without it, anyone holding a device's push token can post notifications to it
through Expo's service. That is a modest risk — tokens are not public — but turn
it on if you care. Get one from your Expo account's dashboard.

Unrelated to `TGTG_API_TOKEN`.

### `TGTG_DEV_MODE`

**Development only. Leave it off in normal use.**

```bash
TGTG_DEV_MODE=1
```

Accepts `1`, `true`, `yes`, `on`, `enabled`. Unlocks the testing affordances
described in [Development](development.md#dev-mode), and prints a warning banner
at startup so you cannot forget it is on.

**Dev mode alone does not raise the polling rate.** The poll floor only drops to
10 seconds when a fixture is also configured — pointing a fast poll at the live
API is exactly the behaviour that gets accounts blocked, so dev mode without a
fixture keeps the production 300-second floor.

---

### `TGTG_DEV_FIXTURE`

**Development only.** Poll items from a local JSON file instead of Too Good To
Go. Requires `TGTG_DEV_MODE`.

```bash
TGTG_DEV_MODE=1
TGTG_DEV_FIXTURE=/absolute/path/to/dev-fixture.json
TGTG_POLL_INTERVAL=20
```

This is how you test the alert path at all: the mechanism is a 0 → >0 stock
transition, and you cannot make a real shop restock on demand. With a fixture you
edit a number and watch the real matcher, database writes, and push fire.

Generate one with:

```bash
tgtg-alert dev fixture --write
```

The file is re-read on every poll, so edits take effect immediately. It can also
simulate failures — see [Development](development.md#testing-failures).

**Setting this without `TGTG_DEV_MODE` is a hard error**, deliberately. The
dangerous half-configuration is believing you are on a fixture while the poller
quietly talks to the live API.

## Deployment examples

**Cautious home setup:**

```bash
TGTG_DATA_DIR=/var/lib/tgtg-alert
TGTG_POLL_INTERVAL=900
TGTG_HOST=127.0.0.1
TGTG_LOG_LEVEL=INFO
TGTG_WEBHOOK_URL=https://ntfy.sh/my-topic
```

**Tightening up after a block:**

```bash
TGTG_POLL_INTERVAL=1800
TGTG_LOG_LEVEL=WARNING
```

Wait a day. If it clears, step the interval back down gradually rather than
returning straight to a fast poll.

**Diagnosing why nothing matches:**

```bash
TGTG_LOG_LEVEL=DEBUG
```

then `tgtg-alert poll --dry-run` and read the per-item lines.
